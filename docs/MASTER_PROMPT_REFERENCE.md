# CozyTrip.kr 신규 개발 마스터 프롬프트

## 아고다 호텔 소개 블로그 자동화 · 아고다 어필리에이트 · Google AdSense · 모던 UI/UX

> **사용 목적:** 이 문서를 코딩 에이전트 또는 AI 개발 도구에 그대로 제공하여, 기존 프로젝트와 파일에 의존하지 않고 `cozytrip.kr`를 위한 완전히 새로운 웹사이트를 별도 디렉터리에서 기획·구현·검증하도록 한다.
>
> **중요한 전제:** 사이트 이름/도메인이 `cozytrip.kr`로 지정되어 있더라도, 실제 콘텐츠와 핵심 기능은 일본 호텔 소개 콘텐츠 및 자동화에 맞춘다. 도메인 이름과 서비스 주제의 불일치가 사용자 신뢰·브랜드·SEO에 미칠 영향을 구현 전에 보고하고, 소유자가 명시적으로 결정하기 전에는 도메인 변경, DNS 변경, 기존 사이트 교체 또는 배포를 실행하지 않는다.

# 1. 역할과 최종 목표

당신은 시니어 풀스택 개발자, 기술 설계자, UX/UI 디자이너, SEO 전문가, 콘텐츠 운영 자동화 엔지니어, 테스트 엔지니어 역할을 동시에 수행한다.

기존 웹사이트, 이전 코드, 기존 프롬프트, 기존 컴포넌트, 이전 데이터 모델 또는 이전 구현 결과를 재사용해야 한다고 가정하지 않는다. **완전히 새로운 프로젝트를 처음부터 설계하고 구현한다.** 다만 작업 공간에 이미 저장소가 존재할 수 있으므로, 기존 자료를 무시한다는 의미는 기존 파일을 삭제하거나 덮어쓴다는 의미가 아니다. 새 프로젝트를 격리된 디렉터리에 만들고, 기존 파일은 명시적인 승인 없이 수정·삭제·이동하지 않는다.

## 1.1 핵심 목표

1. 일본 여행객을 대상으로 한 **일본 호텔 소개 블로그**를 구축한다.
2. 호텔·지역·여행 목적별로 구조화된 콘텐츠를 관리한다.
3. 검증 가능한 데이터와 고유한 편집 관점을 기반으로 호텔 소개 글 초안을 자동 생성한다.
4. 사람이 사실관계, 이미지 권리, 제휴 링크, 문장 품질을 검토하고 승인한 뒤 게시할 수 있는 콘텐츠 파이프라인을 만든다.
5. 아고다(A​​goda) 어필리에이트를 통해 적절한 호텔 예약 페이지로 연결하고 제휴 수익을 추구한다.
6. Google AdSense 정책과 사용자 경험을 고려한 광고 배치를 구현한다.
7. 모던하고 신뢰감 있으며 모바일 우선인 UI/UX를 제공한다.
8. 정적 페이지의 빠른 로딩, 검색엔진 색인 가능성, 접근성, 보안, 유지보수성을 확보한다.
9. API나 제휴 프로그램에 대한 접근 권한이 확인되지 않은 경우에도 수동 데이터 입력 및 검토 가능한 초안 생성 흐름이 작동하도록 설계한다.
10. 테스트와 검증 결과를 실제 실행 결과로 보고하며, 실행하지 않은 항목을 통과했다고 주장하지 않는다.

## 1.2 성공 기준

프로젝트 완료 시 다음이 충족되어야 한다.

- 독립된 프로젝트 디렉터리 안에 재현 가능한 빌드 환경이 존재한다.
- 개발·검증·빌드 명령이 문서화되어 있다.
- 홈, 지역 목록, 지역 상세, 호텔 상세, 카테고리, 검색, 소개/정책 페이지가 작동한다.
- 콘텐츠 모델이 호텔 정보, 출처, 확인 날짜, 이미지 권리 상태, 제휴 링크 상태를 구분한다.
- 자동화 기능은 실제로 검증된 입력을 사용하고, 허위 가격·가용성·평점·편의시설·API 응답을 생성하지 않는다.
- 아고다 API/피드/딥링크는 실제 계정 권한과 공식 문서에 근거해 통합한다. 권한이 없으면 연결 지점과 수동 대체 경로만 구현한다.
- 광고 영역은 콘텐츠를 가리거나 클릭을 유도하도록 오해를 일으키지 않는다.
- 주요 페이지는 모바일·태블릿·데스크톱에서 사용할 수 있다.
- 개인정보처리방침, 쿠키/추적 관련 설명(해당되는 경우), 제휴 고지, 광고 고지, 연락처/운영자 정보 페이지가 마련되어 있다.
- 테스트, 타입 검사, 린트/포맷 검사, 프로덕션 빌드가 실제로 실행되고 결과가 보고된다.
- 기존 프로젝트의 파일을 무단으로 수정하거나 삭제하지 않았다.

# 2. 최우선 실행 규칙

다음 규칙은 다른 요구사항보다 우선한다.

## 2.1 기존 작업 보호

1. 시작하기 전에 현재 작업 디렉터리, 저장소 루트, Git 브랜치, `git status`, 디렉터리 구조를 확인한다.
2. 기존 `cozytrip.kr` 프로젝트가 존재하더라도 이를 기반으로 리팩터링하거나 덮어쓰지 않는다.
3. 저장소 내부에 새 디렉터리(예: `projects/japan-hotel-blog/` 또는 `apps/japan-hotel-blog/`)를 생성해 독립적으로 개발한다. 저장소 구조에 가장 적합한 위치를 선택하되, 선택 이유를 문서화한다.
4. 사용자가 경로를 명시한 경우 그 경로를 우선한다. 경로가 모호하면 기존 파일을 건드리지 않는 안전한 새 하위 디렉터리를 선택한다.
5. `git reset --hard`, `git clean -fd`, 대량 삭제, 강제 체크아웃, 기존 파일 덮어쓰기, 기존 설정 교체를 하지 않는다.
6. 기존 `package.json`, 잠금 파일, 빌드 설정, Cloudflare 설정, GitHub 설정, DNS, 환경변수, 도메인 설정을 수정하지 않는다. 새 프로젝트 전용 설정이 필요하면 새 디렉터리 안에 둔다.
7. 기존 루트 설정과 새 프로젝트 설정이 충돌할 수 있으면 충돌을 보고하고 안전한 격리 방법을 사용한다.
8. 새 디렉터리에서 독립 실행이 가능한지 확인한다. 모노레포의 루트 도구 설정을 의도적으로 공유한다면 의존성과 영향 범위를 문서화한다.
9. 기존 사이트와 새 사이트의 배포 경로, 출력 디렉터리, 환경변수, 도메인을 혼동하지 않는다.
10. 작업 완료 후 `git diff` 및 `git status`를 확인하고 변경 사항을 보고한다.

## 2.2 승인 없는 외부 변경 금지

다음은 명시적인 사용자 승인 없이 실행하지 않는다.

- 프로덕션 배포
- 도메인/DNS 변경
- 기존 웹사이트 교체
- Cloudflare Pages 프로젝트 연결 변경
- 데이터베이스 삭제 또는 마이그레이션
- 실제 사용자에게 이메일 발송
- 실제 제휴 계정의 설정 변경
- 실제 게시물 공개 및 대량 게시
- 유료 서비스 가입 또는 결제
- API 키, 비밀키, 개인 정보의 외부 전송
- 사용자의 계정에서 광고 또는 제휴 링크를 임의로 활성화

## 2.3 사실성 원칙

- 실제로 확인하지 않은 호텔 정보, API 필드, API URL, 예약 링크, 가격, 재고, 객실 유형, 조식 여부, 주차 여부, 역과의 도보 시간, 평점, 리뷰 수, 호텔 운영 상태를 만들어내지 않는다.
- 검색 결과에 나온 내용만으로 확인이 끝났다고 가정하지 않는다.
- 사실과 편집적 설명, 추론, 사용자 입력을 명확히 구분한다.
- 데이터가 없으면 `unknown`, `unverified`, `needs_review` 같은 명시적 상태를 사용한다.
- API가 없거나 권한이 확인되지 않으면 가짜 API 응답을 구현하지 않는다.
- 모든 자동 생성 글에는 검토 상태를 부여하고, 필수 검증이 끝나지 않은 글은 게시할 수 없게 한다.

# 3. 제품 정의와 독자

## 3.1 제품 정의

한국어 사용자가 일본 여행을 계획할 때 호텔 후보를 탐색하고 비교할 수 있도록 돕는 **일본 호텔 정보·여행 콘텐츠 웹사이트**를 구축한다.

단순히 호텔 설명을 대량 복제하는 사이트가 되어서는 안 된다. 독자가 특정 호텔을 선택하는 데 필요한 맥락, 지역 특성, 여행 목적, 교통 접근성 확인 방법, 예약 전에 확인할 항목, 주변 일정 아이디어 등 실질적인 편집 가치를 제공해야 한다.

## 3.2 주요 독자

- 일본 자유여행을 준비하는 한국어 사용자
- 도쿄·오사카·교토·후쿠오카·삿포로 등 특정 지역의 숙소를 찾는 여행객
- 가족 여행, 커플 여행, 혼자 여행, 친구 여행, 비즈니스 여행을 계획하는 사람
- 역 근처, 공항 접근성, 온천, 료칸, 가족 친화성, 장기 숙박 등 구체적인 조건으로 호텔을 찾는 사람
- 호텔 예약 전에 편의시설, 체크인 정책, 위치, 교통, 취소 조건을 비교하고 싶은 사람

## 3.3 브랜드와 도메인 검토

서비스 주제는 일본 호텔 콘텐츠인데 도메인이 `cozytrip.kr`인 경우, 이름이 금융/계산기 서비스를 연상시킬 수 있다. 이 문제를 감추거나 임의로 해결하지 않는다.

구현 초기에 다음을 문서화한다.

- 현재 지정된 도메인과 브랜드의 불일치 가능성
- 검색 사용자 신뢰와 클릭률에 미칠 수 있는 영향
- 기존 도메인을 그대로 사용하는 경우 필요한 명확한 브랜드/사이트 설명
- 향후 별도 도메인을 쓰기로 결정했을 때 필요한 이전·리디렉션 계획
- 기존 운영 사이트에 미칠 수 있는 위험

기본값은 **현재 도메인 설정을 변경하지 않고, 새 프로젝트만 별도 디렉터리에서 개발하는 것**이다. 실제 공개 주소는 사용자가 결정하기 전까지 확정하지 않는다.

# 4. 기술 스택과 개발 제약

프로젝트를 별도 디렉터리에 구축하며, 다음 스택을 기본으로 사용한다. 실제 환경과 도구 버전을 먼저 조사하고, 설치 가능한 안정 버전과 호환성을 확인한 뒤 정확한 버전을 잠금 파일에 고정한다.

## 4.1 기본 스택

- **Astro**: 콘텐츠 중심 사이트, 정적 페이지 생성, 페이지 레이아웃
- **Bun**: 패키지 설치, 스크립트 실행, 테스트 및 개발 워크플로
- **TypeScript**: 데이터 모델, 서버 측/빌드 타임 로직, 자동화 도구
- **UnoCSS**: 유틸리티 기반 스타일링
- **UnoCSS Attributify**: HTML 요소의 속성 형태로 유틸리티 작성
- **Astro Content Collections 또는 검증 가능한 데이터 계층**: 호텔·지역·기사 콘텐츠 관리
- **Bun test 또는 선택한 TypeScript 호환 테스트 도구**: 단위·통합 테스트
- **Cloudflare Pages**: 사용자가 배포 대상으로 확정한 경우 정적 배포 후보

새 프로젝트에서 선택한 기술의 버전, 설치 명령, 호환성, 대안을 `docs/TECHNICAL_DECISIONS.md`에 기록한다.

## 4.2 코드 작성 규칙

1. TypeScript를 기본으로 사용한다.
2. 일반 JavaScript 파일을 새로 작성하지 않는다. 도구가 반드시 요구하는 설정 파일 예외가 필요하면 이유를 문서화하고 가능한 TypeScript/ESM 대안을 먼저 검토한다.
3. 일반 CSS 파일과 광범위한 사용자 정의 CSS를 작성하지 않는다. UnoCSS 유틸리티, Attributify, 토큰, 프리셋, 컴포넌트로 해결한다.
4. 브라우저에서 실행하는 코드가 필요할 때는 Astro 컴포넌트 내부의 타입이 지정된 스크립트나 검증된 TypeScript 모듈을 사용한다.
5. 프레임워크 기능을 불필요하게 클라이언트 하이드레이션하지 않는다. 가능한 한 정적 HTML로 제공한다.
6. UI가 실제로 상호작용해야 할 때만 최소한의 클라이언트 스크립트를 사용한다.
7. 데이터 검증은 TypeScript 타입만 믿지 말고, 외부 입력과 파일 데이터에는 런타임 스키마 검증을 적용한다.
8. 프로젝트 전용 설정과 스크립트는 새 디렉터리 내부에 둔다.
9. `any`를 무분별하게 사용하지 않는다. 외부 API 응답은 `unknown`으로 받고 검증한 후 사용한다.
10. 오류를 숨기는 광범위한 `catch`와 무시되는 Promise를 만들지 않는다.
11. 타입 단언으로 검증을 우회하지 않는다.
12. 의미 있는 함수와 모듈을 작게 나누되, 단순한 코드까지 과도하게 추상화하지 않는다.
13. 포맷터와 정적 검사를 실제로 실행하고 결과를 확인한다.
14. 재현 가능한 설치를 위해 Bun 잠금 파일을 저장소에 포함한다.
15. 운영 비밀값을 소스 코드, 공개 환경변수, 콘텐츠 파일, 로그에 넣지 않는다.

  <h2 text="lg md:xl" font="semibold" leading="snug">
    호텔 소개 제목
  </h2>
  <p mt="2" text="sm neutral-600 dark:neutral-300" leading="7">
    출처와 확인 날짜를 기준으로 작성한 설명입니다.
  </p>

- 예시는 설명용이다. UnoCSS에서 실제 지원하는 문법인지 빌드 결과로 검증한다.
- 프로젝트 전체에서 일관된 Attributify 작성 방식을 유지한다.
- 같은 요소에서 조합할 수 있는 유틸리티는 합리적으로 같은 속성에 모은다.
- 사용자 정의 CSS로 문제를 해결하기 전에 UnoCSS 프리셋과 토큰 구성을 검토한다.

## 4.4 다크 모드와 모션

- 기본 다크 모드는 OS 설정을 따른다.
- 다크 모드에서 본문, 카드, 경계, 링크, 광고 자리, 입력 필드의 대비를 점검한다.
- `prefers-reduced-motion`을 존중한다.
- 페이지 진입을 방해하는 과도한 애니메이션, 스크롤 가로채기, 자동 재생 영상을 사용하지 않는다.
- 애니메이션은 짧은 hover/focus/active 피드백에 한정한다.
- 일반적인 정보 탐색 사이트에 불필요한 SPA 전환을 강제하지 않는다.

# 6. 사이트 정보 구조(IA)

## 6.1 필수 페이지

### 홈

- 명확한 사이트 소개와 여행자에게 제공하는 가치
- 일본 주요 여행 지역 탐색
- 편집자가 선정한 호텔 가이드 또는 여행 목적별 큐레이션
- 최근 검토된 콘텐츠
- 목적별 카테고리
- 검색 입력 및 탐색 진입점
- 제휴/광고로 수익을 얻을 수 있음을 숨기지 않는 적절한 고지
- 광고를 콘텐츠처럼 위장하지 않는 레이아웃

### 지역 목록 페이지

예: `/regions/`

- 일본 지역을 명확하게 분류
- 도시 또는 지역 카드
- 지역별 핵심 특징과 적합한 여행 유형
- 지역별 호텔 콘텐츠 수
- 관련 가이드 링크
- 중복된 얇은 페이지를 대량 생성하지 않음

### 지역 상세 페이지

예: `/regions/tokyo/`, `/regions/osaka/`

- 지역 개요와 여행 스타일
- 교통 및 숙소 위치를 판단하는 데 도움이 되는 정보
- 지역 안의 세부 지역/역세권/관광권
- 엄선한 호텔 콘텐츠
- 여행 일정 가이드
- 데이터의 출처와 확인 시점
- 해당 지역을 처음 방문하는 여행자를 위한 FAQ
- 관련 지역 링크

### 호텔 목록/검색 페이지

예: `/hotels/`, `/search/`

- 호텔 이름, 지역, 숙박 스타일, 편의시설 등 실제로 검증 가능한 필드 기준으로 검색/필터
- 결과 수와 필터 상태 표시
- 필터 초기화
- 모바일에서 사용하기 쉬운 필터 인터페이스
- 결과 없음 상태와 검색 오류 상태를 명확하게 표시
- 실제 지원하지 않는 정렬/필터를 UI에 노출하지 않음
- 정적 사이트에서 가능한 검색 방식과 규모 한계를 문서화

### 호텔 상세 페이지

예: `/hotels/tokyo/example-hotel/`

필수 영역:

1. 호텔명과 위치
2. 핵심 요약 및 “이 호텔을 고려할 만한 여행자” 설명
3. 검증된 특징과 주의할 점
4. 위치와 교통 정보(출처가 있는 경우에만 구체적인 시간/거리 표시)
5. 객실/편의시설 정보(검증된 항목만)
6. 가족·커플·혼자·비즈니스 등 여행 목적 적합성(근거가 있는 편집 판단임을 표시)
7. 주변 관광지 또는 식사 정보(검증된 출처가 있는 경우)
8. 예약 전에 확인할 사항
9. 가격·객실 재고·취소 조건은 예약 시점과 숙박 날짜에 따라 달라진다는 안내
10. 아고다 제휴 링크 또는 예약 버튼(권한과 링크가 검증된 경우에만)
11. 광고 영역(광고 정책과 UX를 준수하는 경우)
12. 관련 호텔과 지역 가이드
13. 정보 출처, 마지막 확인 날짜, 편집/검토 상태
14. 제휴 관계 고지

호텔 상세 페이지는 원본 데이터가 부족하면 자동으로 공개하지 않는다. 모든 필드가 채워져 보이도록 허위 내용을 채우지 않는다.

### 여행 가이드 페이지

예: `/guides/tokyo-first-trip/`, `/guides/kyoto-ryokan-guide/`

- 호텔 소개만 반복하지 않고 실질적인 여행 질문에 답한다.
- 작성 목적과 독자 문제를 명확히 한다.
- 지역별 숙소 선택 기준, 교통 고려 사항, 예약 전 확인 항목, 여행 일정 구성 등 독창적 편집 가치를 포함한다.
- 날짜에 민감한 내용에는 확인 날짜를 표시한다.
- 공식 기관/교통 운영자/호텔 공식 페이지 등 신뢰 가능한 출처를 우선한다.

### 카테고리 페이지

예시:

- 역 접근성이 중요한 호텔
- 온천·료칸
- 가족 여행
- 커플 여행
- 혼자 여행
- 공항 이동이 편리한 숙소
- 장기 숙박
- 비즈니스 여행

카테고리는 검증된 태그와 편집 기준을 통해 생성한다. 키워드만 바꾼 유사 페이지를 대량으로 만들지 않는다.

### 필수 정책/운영 페이지

- 사이트 소개
- 문의
- 편집 원칙 및 사실 검증 정책
- 아고다 어필리에이트/제휴 고지
- 개인정보처리방침
- 이용약관
- 광고 및 추적 기술에 대한 안내(실제 사용하는 기술과 법적 검토에 맞게)
- 오류 제보 및 정보 수정 요청 방법

법률 자문을 받은 것처럼 표현하지 않는다. 실제 운영 국가, 사용 기술, 광고 플랫폼 정책에 맞게 운영자가 최종 검토해야 한다.

# 7. 모던 UI/UX 디자인 시스템

## 7.1 디자인 방향

다음 키워드를 기준으로 시각 디자인을 구성한다.

- 모던하고 정돈된 편집 디자인
- 일본 여행 매거진의 분위기
- 넓은 여백과 명확한 타이포그래피
- 고품질의 합법적으로 사용 가능한 이미지
- 정보 우선순위가 분명한 카드와 섹션
- 신뢰할 수 있는 정보와 출처 표시
- 차분하고 세련된 색상
- 빠르고 부담 없는 탐색
- 모바일에서 자연스러운 단일 열 레이아웃
- 데스크톱에서 과도하게 넓지 않은 읽기 영역

특정 경쟁 사이트를 복제하지 않는다. 타 사이트의 브랜드, 이미지, 고유한 문구, 레이아웃을 그대로 가져오지 않는다.

## 7.2 색상과 시각 토큰

초기 제안:

- 기본 배경: 밝은 웜 화이트/오프화이트
- 기본 텍스트: 높은 대비의 차콜
- 보조 텍스트: 읽기 쉬운 중간 회색
- 주요 포인트: 딥 인디고 또는 잉크 네이비
- 보조 포인트: 차분한 세이지/청록 또는 절제된 일본식 주홍색
- 테두리: 낮은 대비의 중성 색상
- 상태 색상: 성공·경고·오류를 색상 외의 텍스트/아이콘으로도 구분
- 다크 모드: 동일한 정보 위계와 충분한 대비를 유지하는 별도 토큰

색상 값은 UnoCSS 테마/프리셋 설정에서 관리한다. 임의의 인라인 색상이나 요소별로 제각각인 색상 사용을 피한다. 색상 선택은 WCAG 대비 검증을 거친다.

## 7.3 타이포그래피

- 한국어 본문에 적합한 시스템 폰트 스택을 우선한다.
- 웹폰트를 사용할 경우 라이선스와 자체 호스팅 가능 여부를 확인한다.
- 본문 글자 크기, 줄 높이, 문단 너비를 읽기 쉽게 설정한다.
- 제목 단계(h1-h6)는 의미와 시각적 위계를 일치시킨다.
- 과도한 글자 크기, 과도한 굵기, 모든 텍스트의 대문자 스타일 등을 사용하지 않는다.
- 긴 호텔 설명과 가이드는 적절한 최대 너비와 문단 간격을 유지한다.

## 7.4 레이아웃과 반응형 기준

최소한 다음 구간을 점검한다.

- 작은 모바일: 약 320–374px
- 일반 모바일: 약 375–767px
- 태블릿: 약 768–1023px
- 데스크톱: 약 1024–1439px
- 넓은 데스크톱: 1440px 이상

구간은 예시이며 실제 콘텐츠가 자연스럽게 흐르는지 테스트해 조정한다.

필수 UX:

- 모바일에서 콘텐츠가 가로로 넘치지 않아야 한다.
- 클릭/터치 대상은 충분한 크기와 간격을 가져야 한다.
- 내비게이션은 키보드 및 스크린 리더로 사용할 수 있어야 한다.
- 검색과 필터는 터치 조작이 쉬워야 한다.
- 모바일 광고가 본문을 가리거나 닫기 어려운 형태가 되지 않도록 한다.
- 데스크톱에서 과도한 여백이나 지나치게 넓은 본문을 피한다.
- 이미지 비율과 카드 높이가 일관적이어야 한다.
- 긴 페이지에서도 목차/앵커가 유용하게 작동해야 한다.

## 7.6 상호작용과 상태

- 링크와 버튼의 역할을 의미에 맞게 구분한다.
- 외부 예약 링크에는 새 탭 여부와 외부 이동을 사용자에게 명확히 전달한다.
- 버튼은 클릭 후 실제 동작이 있어야 한다.
- 비활성 상태, 로딩 상태, 오류 상태, 결과 없음 상태를 구현한다.
- 검색/필터 조건은 사용자가 확인하고 초기화할 수 있어야 한다.
- 입력 오류는 필드 근처에서 설명한다.
- 포커스 표시를 제거하지 않는다.
- 키보드만으로 모든 핵심 탐색이 가능해야 한다.
- `aria-label`을 남용하지 않고 실제 의미를 설명한다.
- 색상만으로 상태를 전달하지 않는다.
- 동작이 없는 UI 요소나 장식용 버튼을 만들지 않는다.

## 7.7 이미지 디자인과 권리

- 호텔 이미지에는 명확한 사용 권한이 있어야 한다.
- 아고다 페이지에서 이미지를 임의로 다운로드해 복제하거나, 타 사이트의 이미지를 무단 수집하지 않는다.
- API가 이미지 사용을 허용하는지, 허용 범위와 표시 조건을 공식 문서에서 확인한다.
- 이미지 출처, 권리 상태, 필수 크레딧, 사용 기한/제한을 데이터로 관리한다.
- 권리가 확인되지 않은 이미지는 프로덕션 콘텐츠에서 제외한다.
- 이미지가 없으면 정돈된 플레이스홀더를 사용하고 실제 호텔 사진처럼 오해시키지 않는다.
- 모든 콘텐츠 이미지에 의미 있는 대체 텍스트를 제공한다. 장식 이미지는 빈 alt를 사용한다.
- 반응형 이미지, 명시적 크기, 적절한 포맷, 지연 로딩을 사용한다.
- 첫 화면의 주요 이미지에는 무조건 지연 로딩을 적용하지 말고 성능을 측정해 결정한다.
- 이미지를 제공하는 공식 API의 요구 사항이 일반적인 UI 요구보다 우선한다.

# 8. 호텔 콘텐츠 데이터 모델

콘텐츠는 단순한 Markdown 문서만으로 관리하지 말고, 호텔의 구조화 데이터와 편집 콘텐츠를 분리한다. 필요하면 JSON/YAML/Markdown 조합을 사용하되 런타임/빌드 시 검증한다.

## 8.1 호텔 레코드

권장 필드:

- `id`: 내부에서 안정적으로 사용하는 고유 ID
- `slug`: URL에 사용하는 고유한 경로
- `name`: 공식 호텔명
- `nameKana` 또는 `nameLocal`: 공식 표기(검증된 경우)
- `nameKo`: 한국어 표기(공식 표기가 아니면 편집상 표기임을 명시)
- `country`
- `prefecture`
- `city`
- `district`
- `address`
- `officialWebsiteUrl`
- `agodaPropertyId`: 실제 확인한 경우에만
- `agodaDeepLink`: 생성 규칙/권한이 검증된 경우에만
- `affiliateStatus`: `not_configured | pending | verified | disabled`
- `summary`
- `editorialSummary`
- `suitableFor`: 근거를 기록한 편집 태그
- `features`: 검증된 특징 목록
- `amenities`: 출처가 있는 편의시설
- `transport`: 출처와 기준점이 있는 교통 정보
- `nearbyPlaces`: 출처가 있는 주변 장소
- `roomInformation`: 공식적으로 확인된 정보만
- `checkInPolicy`
- `checkOutPolicy`
- `cancellationPolicyNote`
- `priceNote`: 특정 가격을 저장할 때의 날짜/통화/조건을 포함하거나, 가격을 저장하지 않고 변동 안내만 표시
- `images`: 이미지 레코드 배열
- `sources`: 출처 배열
- `firstPublishedAt`
- `lastReviewedAt`
- `reviewStatus`
- `editor`
- `contentVersion`
- `createdAt`
- `updatedAt`

모든 필드가 필수일 필요는 없다. 중요한 것은 필드가 없는 경우를 정상적으로 표현하고, 미확인 값을 거짓으로 채우지 않는 것이다.

## 8.2 출처 레코드

각 출처는 가능한 한 다음을 기록한다.

- `sourceId`
- `sourceType`: `official_hotel | official_tourism | official_transport | authorized_affiliate_api | licensed_provider | other`
- `title`
- `url`
- `publisher`
- `accessedAt`
- `publishedAt` 또는 `updatedAt`(확인 가능한 경우)
- `supports`: 어떤 주장/필드를 뒷받침하는지
- `reliability`
- `usagePermission`: 해당 콘텐츠/이미지를 재사용할 수 있는지
- `notes`

URL만 붙여 두지 말고 출처가 어떤 사실을 뒷받침하는지 기록한다. 웹페이지의 존재가 재사용 권한을 뜻하지 않는다.

## 8.3 이미지 레코드

- `url` 또는 로컬 자산 경로
- `alt`
- `credit`
- `sourceUrl`
- `licenseStatus`
- `permissionEvidence`
- `requiredAttribution`
- `lastCheckedAt`
- `width`
- `height`
- `usageRestrictions`

`licenseStatus`는 예를 들어 `verified`, `pending`, `prohibited`, `unknown`으로 제한한다. `verified`가 아닌 이미지는 공개 빌드에서 제외하거나 안전한 플레이스홀더로 교체한다.

## 8.4 검토 상태

상태 예시:

- `draft`: 초안
- `needs_sources`: 출처 보강 필요
- `needs_fact_check`: 사실 확인 필요
- `needs_image_review`: 이미지 권리 확인 필요
- `needs_affiliate_review`: 제휴 링크 확인 필요
- `approved`: 게시 승인
- `published`: 게시됨
- `archived`: 보관

상태 전이 규칙을 정의한다. 필수 검증이 누락된 상태에서 `approved` 또는 `published`로 전환할 수 없게 한다.

## 8.5 콘텐츠 검증 규칙

빌드/검증 스크립트는 최소한 다음을 확인한다.

- 필수 식별자와 slug 중복
- 내부 링크의 존재
- URL 스킴이 `https:` 또는 허용된 안전한 경로인지
- 잘못된/빈 제목
- 출처 없는 구체적인 호텔 사실
- 확인되지 않은 이미지 권리
- 깨진 제휴 링크 또는 비정상 링크 형식
- 필수 제휴 고지 누락
- 오래된 `lastReviewedAt`
- 게시 승인 없이 공개 대상에 포함된 글
- 빈 FAQ, 빈 섹션, 의미 없는 반복 콘텐츠
- 페이지별 고유 title/description 누락
- 콘텐츠 내 테스트 데이터 또는 placeholder 텍스트가 남아 있는지
- JSON-LD가 페이지의 실제 화면 콘텐츠와 일치하는지

# 9. 호텔 소개 글 작성 원칙

## 9.1 콘텐츠 품질

모든 글은 독자의 구체적인 질문을 해결해야 한다. 호텔 이름과 일반적인 홍보 문구만 바꾸어 여러 페이지를 생성하지 않는다.

각 글에는 적어도 다음 요소를 포함하도록 편집 기준을 설정한다.

1. 이 호텔을 검토하는 독자에게 필요한 한 문단 요약
2. 어떤 여행자에게 적합할 수 있는지와 그 판단 근거
3. 위치·교통을 이해하기 위한 맥락
4. 확인된 시설과 실제로 중요한 제한 사항
5. 예약 전에 공식 페이지/예약 페이지에서 재확인할 사항
6. 비슷한 선택지와 비교할 때 확인할 기준
7. 정보 출처와 마지막 확인 날짜
8. 관련 지역 가이드 또는 여행 콘텐츠
9. 제휴 관계 고지
10. 가격·재고·정책이 변할 수 있다는 설명

이 목록을 기계적으로 채우기 위해 사실을 만들어내지 않는다. 근거가 없는 섹션은 생략하거나 “공식 정보에서 확인 필요”로 표시한 검토용 초안에 남긴다.

## 9.2 문체

- 자연스럽고 명확한 한국어
- 과장 광고나 무근거 최상급 표현 금지
- 반복되는 서론과 결론 금지
- 실제 여행자의 의사결정을 돕는 구체적 정보
- 확실한 사실과 편집적 의견 구분
- 광고 문구처럼 보이는 표현을 줄이고 장단점을 균형 있게 설명
- 출처가 확인되지 않은 “완벽한”, “최고”, “무조건 추천” 등의 단정 표현을 피함
- 독자에게 직접적으로 도움이 되는 설명 사용
- 같은 템플릿의 문장을 호텔마다 그대로 반복하지 않음

## 9.3 검색 의도와 고유 가치

SEO를 위해 키워드만 반복하지 않는다. 각 페이지가 해결하는 검색 의도를 정의한다.

예:

- 지역 + 호텔: 해당 지역 숙박 후보 탐색
- 역 + 숙소: 교통 접근성 판단
- 여행 목적 + 호텔: 목적에 맞는 후보 비교
- 호텔 이름 + 후기/정보: 공식 정보와 예약 전 확인 항목 파악
- 지역 숙소 선택 가이드: 지역별 장단점과 숙박 위치 판단

실제 후기나 투숙 경험이 없는 경우 직접 숙박한 것처럼 쓰지 않는다. “실제 투숙 후기”, “직접 경험”, “현장 방문” 등의 표현은 검증 가능한 경험이 있을 때만 사용한다.

## 9.4 AI 콘텐츠 사용

AI는 구조화된 자료를 요약하고, 초안을 만들고, 누락 항목을 찾는 데 사용한다. AI 출력은 자동으로 사실이 되지 않는다.

자동화 파이프라인은 다음을 지원해야 한다.

- 입력 데이터 검증
- 출처별 주장 연결
- 미확인 정보 경고
- 중복 문장/유사 문서 탐지
- 키워드 과다 반복 검사
- 과장 표현 탐지
- 링크/이미지 권리 검토
- 사람의 수정 및 승인
- 게시 후 정기적인 정보 재검토

공개용 글을 만들 때는 검토를 통과한 사실만 사용한다. 검토를 통과하지 못한 초안은 공개 빌드에서 제외한다.

# 10. 콘텐츠 자동화 파이프라인

## 10.1 설계 목표

자동화는 “AI가 글을 대량으로 생성해 무조건 게시”하는 시스템이 아니다. **검증 가능한 데이터를 수집·정리하고, 근거가 표시된 초안을 만들며, 사람이 승인한 글만 배포하는 콘텐츠 운영 시스템**이다.

## 10.2 단계

### 단계 A: 대상 선정

- 도시/지역과 여행 의도를 선택한다.
- 중복 호텔 및 중복 주제를 확인한다.
- 사이트에서 해당 페이지를 만들 만한 독자 가치가 있는지 판단한다.
- 출처를 확보할 수 없는 대상은 자동화 대상에서 보류한다.

### 단계 B: 데이터 입력/수집

허용된 데이터 경로:

- 운영자가 직접 입력한 데이터
- 호텔 공식 웹사이트에서 이용 약관에 따라 확인한 정보
- 공식 관광/교통 기관의 재사용 가능한 정보
- 계정 권한과 문서상 허용 범위가 확인된 아고다 API/피드/제휴 도구
- 명시적으로 재사용 허가를 받은 제3자 데이터

금지:

- 접근 권한 없는 비공개 API 사용
- 로그인/접근 제한 우회
- CAPTCHA 또는 속도 제한 우회
- 웹사이트 약관을 위반하는 대량 스크래핑
- 이미지/리뷰/가격 데이터를 무단 복제
- 허위 데이터를 테스트를 위해 실제 데이터처럼 저장
- API를 사용하지 않았는데 사용했다고 기록

### 단계 C: 정규화와 검증

- 문자열과 URL 정리
- ID와 slug 충돌 검사
- 출처별 데이터 필드 매핑
- 출처의 신뢰도 및 접근 날짜 기록
- 필드별 검증 상태 기록
- 값이 상충하면 자동으로 임의 선택하지 않고 검토 큐에 보낸다.
- 시간이 민감한 정보는 만료/재확인 정책을 적용한다.

### 단계 D: 초안 생성

초안 생성기는 다음 입력을 받아야 한다.

- 검증된 호텔 레코드
- 각 사실을 뒷받침하는 출처
- 콘텐츠 템플릿/편집 기준
- 지역 맥락 자료
- 내부 링크 후보
- 금지된 표현과 필수 고지

출력은 구조화된 결과로 만든다.

- 제목 후보
- 메타 설명
- 요약
- 본문 섹션
- 확인된 특징
- 확인이 필요한 항목
- FAQ 초안(근거가 있는 경우)
- 내부 링크 후보
- 제휴 CTA 문구
- 출처 목록
- 자동 품질 검사 결과
- 검토 상태

초안 생성 결과는 반드시 `draft` 상태로 저장한다.

### 단계 E: 품질 검사

자동 검사는 다음을 평가한다.

- 모든 구체적 사실에 근거가 있는가?
- 출처 URL이 존재하고 해당 주장과 관련이 있는가?
- 호텔명, 주소, 지역이 서로 모순되지 않는가?
- 가격/재고/평점을 현재 값처럼 단정하지 않는가?
- 호텔 사진의 사용 권한이 확인되었는가?
- 제휴 링크가 검증되었는가?
- 글이 다른 호텔 페이지와 지나치게 유사하지 않은가?
- 제목과 본문이 검색 의도에 맞는가?
- 콘텐츠가 실제 독자에게 추가 가치를 주는가?
- 제휴 고지와 광고 관련 고지가 필요한 위치에 있는가?
- 빈 템플릿 문구가 남아 있지 않은가?

검사 점수만으로 자동 게시를 허용하지 않는다.

### 단계 F: 사람의 검토

검토자는 다음을 확인한다.

- 공식 호텔 정보
- 출처와 문장 사이의 관계
- 이미지 권리
- 위치·교통 설명
- 편집적 판단의 타당성
- 중복성 및 독창성
- 제휴 링크의 도착 페이지
- 광고 배치
- 오탈자와 한국어 자연스러움
- 날짜에 민감한 내용

승인자는 검토 상태와 검토 일자를 기록한다.

### 단계 G: 게시

- 승인된 콘텐츠만 빌드에 포함한다.
- 배포 전 링크와 이미지 권리를 재검증한다.
- 사이트맵과 내부 링크를 갱신한다.
- 실제 배포 후 페이지 상태를 확인한다.
- 실패하면 자동으로 공개 상태를 잘못 기록하지 않는다.

기본 구현은 로컬에서 실행 가능한 초안 생성/검증 도구와 승인 가능한 Markdown/JSON 결과를 제공한다. CMS나 외부 AI API가 필요하면 비용, 비밀키, 데이터 전송, 약관을 검토한 뒤 선택 사항으로 둔다.

## 10.3 자동화 명령 예시

실제 구현 시 다음과 비슷한 스크립트 명령을 제공한다. 이름은 프로젝트 구조에 맞게 조정할 수 있다.

```bash
bun run content:validate
bun run content:report
bun run content:draft -- --hotel-id example-hotel
bun run affiliate:audit
bun run images:audit
bun run test
bun run check
bun run build
```

- 실행하지 않은 명령의 성공 여부를 문서에 미리 표시하지 않는다.
- `content:draft`는 기본적으로 공개 파일을 덮어쓰지 않는다.
- 기존 초안을 덮어써야 할 경우 백업 또는 명시적 `--overwrite` 옵션을 요구한다.
- 외부 API를 호출하는 스크립트는 `--dry-run`을 제공하고, 호출 대상과 데이터 범위를 출력한다.
- API 호출 횟수와 실패 원인을 기록하되 비밀값과 개인정보를 로그에 출력하지 않는다.

# 11. Agoda 어필리에이트 통합

## 11.1 통합 전 확인 사항

아고다 어필리에이트의 기능, 계정 권한, API 버전, 필드, 엔드포인트, 인증 방식, 이용 제한은 계정과 프로그램 정책에 따라 달라질 수 있다. 실제 사용 가능한 기능을 확인하지 않고 특정 API가 활성화되어 있다고 가정하지 않는다.

통합 전에 다음을 확인하고 `docs/AFFILIATE_SETUP.md`에 기록한다.

- 계정이 승인되었는가?
- 현재 사용 가능한 프로그램/제품이 무엇인가?
- Affiliate Lite API 또는 다른 API에 대한 실제 접근 권한이 있는가?
- 공식 최신 문서와 버전은 무엇인가?
- 인증 방식과 API 키의 범위는 무엇인가?
- 호텔 검색과 호텔 상세 데이터의 권한 범위는 무엇인가?
- 딥링크 생성 방식은 무엇인가?
- 이미지 사용 권한과 표시 조건은 무엇인가?
- 가격/재고 데이터 사용에 대한 제한은 무엇인가?
- 캐싱/갱신/요청 제한이 있는가?
- 링크의 제휴 식별자와 추적 방식은 무엇인가?
- 콘텐츠 또는 광고 표시와 관련한 필수 고지 조건은 무엇인가?
- 승인된 도메인/사이트가 지정되어야 하는가?

사용자가 공식 문서 파일을 제공한 경우 해당 파일을 우선 검토하고, 문서에 없는 내용을 임의로 보충하지 않는다. 최신 정보 확인이 필요하면 공식 아고다/파트너 문서만을 우선적으로 조사하고 확인 날짜를 기록한다.

## 11.2 API 구현 규칙

- API 엔드포인트와 요청/응답 필드는 실제 공식 문서 또는 성공적으로 검증한 응답에 근거한다.
- API 클라이언트는 `src/lib/affiliate/` 또는 그에 상응하는 모듈로 분리한다.
- API 응답은 `unknown`으로 받고 런타임 검증을 통과한 데이터만 내부 모델로 변환한다.
- 네트워크 오류, 타임아웃, 401/403, 속도 제한, 5xx, 빈 결과, 잘못된 JSON을 처리한다.
- 실패 시 빈 호텔 데이터나 가짜 예약 링크를 만들어 내지 않는다.
- 비밀 API 키는 서버/빌드 환경에만 보관한다. `PUBLIC_` 접두사를 붙여 브라우저에 노출하지 않는다.
- 브라우저에 공개되어야 하는 링크와 서버 비밀값을 구분한다.
- API 요청을 정적 빌드 시점에 실행할 경우 API 장애가 전체 빌드를 무조건 실패시키는지, 안전한 대체 정책이 필요한지 설계한다.
- 최신 가격이나 재고가 실시간으로 확인되지 않으면 가격/재고를 현재 값처럼 표시하지 않는다.
- API의 콘텐츠 사용 조건을 위반하는 장기 캐싱을 하지 않는다.
- 제휴 링크를 검증할 수 없는 경우 CTA를 표시하지 않거나 검토용으로만 표시한다.

## 11.3 호텔 링크 전략

- 공식적으로 허용된 딥링크/호텔 링크 생성 방법을 사용한다.
- `agodaPropertyId`는 검증된 값만 저장한다.
- 호텔 이름만으로 임의의 URL을 조합해 올바른 호텔 페이지라고 가정하지 않는다.
- URL을 생성했다면 대상 URL, 생성 방법, 확인 날짜, 상태를 기록한다.
- 링크 검사 도구는 추적 매개변수와 제휴 ID를 제거하거나 변경하지 않는다.
- 제휴 링크 리디렉션을 사용해야 한다면 프로그램 정책에 허용되는지 확인한다.
- 사용자에게 광고/제휴 링크라는 사실을 알아보기 쉽게 표시한다.
- 외부 링크 보안 속성은 프레임워크의 안전한 기본값을 검토하고, 새 탭을 여는 경우 `rel` 속성을 적절히 설정한다.
- 클릭 유도 문구는 사실에 기반하며 “최저가 보장” 같은 검증되지 않은 보장을 사용하지 않는다.

## 11.4 예약 CTA

CTA는 다음을 만족해야 한다.

- 링크 대상이 명확하다.
- 예약 페이지로 이동한다는 사실을 숨기지 않는다.
- 광고성 링크라는 사실을 고지한다.
- 페이지에서 확인하지 못한 가격/재고/혜택을 약속하지 않는다.
- 모바일에서도 조작하기 쉽다.
- 본문과 혼동되는 스타일로 광고를 위장하지 않는다.
- 키보드 접근이 가능하다.
- 링크가 비활성화된 경우 CTA를 숨기거나 이유를 설명한다.

# 12. Google AdSense 통합

## 12.1 정책 우선

AdSense 승인과 수익은 보장할 수 없다. 승인 여부는 Google의 심사와 현재 정책에 달려 있다. 단순한 AI 생성 콘텐츠 대량 게시, 복제된 호텔 설명, 출처 없는 정보, 빈 페이지, 과도한 광고, 오해를 일으키는 UI를 피한다.

AdSense를 활성화하기 전에 현재 공식 정책을 확인하고 `docs/ADSENSE_SETUP.md`에 확인 날짜와 링크를 기록한다.

확인할 항목:

- 사이트 콘텐츠와 가치 기준
- 게시자 정책
- 광고 배치 및 클릭 유도 금지 규정
- 개인정보 및 동의 요구 사항
- 쿠키 및 광고 개인화 관련 설명
- `ads.txt` 요구사항과 설정
- 사이트 검토 절차
- 광고 코드와 자동 광고/수동 광고의 차이
- 모바일 화면에서의 광고 배치
- 광고가 내비게이션/콘텐츠와 혼동되지 않는지

정책 내용을 추측하지 말고 공식 문서에 근거한다.

## 12.2 광고 컴포넌트

재사용 가능한 `AdSlot`을 만든다.

권장 광고 위치 후보:

- 콘텐츠 목록 사이의 중간 광고
- 긴 가이드 본문 내 적절한 구간
- 호텔 상세 콘텐츠의 본문과 시각적으로 분리된 영역
- 필요 시 사이드바(데스크톱에서만)

광고 슬롯은 환경변수 또는 설정을 통해 활성/비활성을 제어할 수 있게 한다. 실제 광고 클라이언트 ID와 슬롯 ID가 없으면 자리 표시자 또는 비활성 상태로 보여 주며, 광고 코드가 없는 상태를 광고가 정상 표시된 것으로 보고하지 않는다.

## 12.3 광고 UX 제한

- 광고를 콘텐츠나 예약 버튼처럼 위장하지 않는다.
- 광고 클릭을 요청하거나 클릭을 유도하지 않는다.
- 콘텐츠보다 광고가 페이지를 압도하지 않도록 한다.
- 레이아웃 이동(CLS)을 줄이기 위해 가능한 경우 광고 컨테이너 공간을 확보한다.
- 모바일 화면을 가리는 임의의 고정 광고를 만들지 않는다.
- 광고가 없는 경우 빈 공간을 과도하게 남기지 않는다.
- 광고 슬롯의 실제 작동은 운영자 계정과 승인 상태에서 별도로 확인한다.
- 개발/테스트 환경에서는 광고 클릭을 유도하거나 실제 광고와 혼동될 수 있는 모형을 사용하지 않는다.

## 12.4 광고와 제휴 링크의 구분

AdSense 광고와 아고다 제휴 링크는 서로 다른 수익 경로다. 각각의 목적과 표시를 구분하고, 제휴 예약 버튼을 일반 콘텐츠 링크처럼 위장하지 않는다. 광고 클릭과 예약 전환을 혼동하는 추적 로직을 만들지 않는다.

# 13. SEO 및 구조화 데이터

## 13.1 기본 SEO

각 페이지에 다음을 구현한다.

- 고유하고 설명적인 `<title>`
- 고유한 meta description
- canonical URL
- robots 메타/정책
- Open Graph 메타데이터
- SNS 공유 이미지(권리가 확인된 이미지)
- sitemap
- robots.txt
- 명확한 제목 계층
- 내부 링크
- breadcrumbs
- 올바른 HTTP 상태와 존재하지 않는 페이지 처리
- 모바일 친화적 레이아웃
- 빠른 로딩
- 중복 페이지 관리
- 언어 선언 `lang="ko"`
- 실제 페이지 내용과 일치하는 메타데이터

배포 도메인이 확정되기 전에는 프로덕션 canonical과 sitemap 도메인을 하드코딩하지 않는다. 기본 도메인은 환경별 설정으로 관리하고, 임시 주소가 프로덕션 주소로 색인되지 않도록 한다.

## 13.2 호텔/여행 페이지 SEO

- 호텔명, 지역, 여행 목적을 자연스럽게 제목과 본문에 반영한다.
- 키워드 반복을 위해 부자연스러운 문장을 만들지 않는다.
- 비슷한 호텔 페이지를 기계적으로 대량 생성하지 않는다.
- 각 페이지의 독자 가치와 고유 정보를 확인한다.
- 실제 투숙 경험이 없는 경우 리뷰 콘텐츠처럼 표시하지 않는다.
- 검색 엔진에 보이는 내용과 사용자에게 보이는 내용이 일치하도록 한다.
- 허위 평점이나 가짜 리뷰 구조화 데이터를 사용하지 않는다.
- 검색엔진을 속이기 위한 doorway page, cloaking, 숨겨진 텍스트를 만들지 않는다.

## 13.3 구조화 데이터

필요에 따라 `Organization`, `WebSite`, `BreadcrumbList`, `Article` 등 실제 페이지 내용과 일치하는 스키마를 검토한다.

호텔 관련 구조화 데이터는 해당 스키마의 현재 지원 범위와 Google의 최신 지침을 확인한 뒤 사용한다. 구조화 데이터는 검색 결과에 특정 표시가 나온다는 보장이 아니다.

- 실제 페이지에 없는 평점/가격/리뷰를 넣지 않는다.
- 작성자, 게시일, 수정일은 실제 값만 사용한다.
- JSON-LD를 HTML에 안전하게 삽입한다.
- 사용자 입력 문자열로 인한 스크립트 삽입 위험을 방지한다.
- 빌드 테스트에서 JSON-LD 파싱과 필수 필드 일관성을 확인한다.

## 13.4 검색 색인 품질 게이트

게시 가능한 페이지는 다음을 통과해야 한다.

- 본문이 비어 있지 않음
- 페이지별 고유한 제목/설명
- 적절한 canonical
- 출처 및 확인 시점(정보 유형에 따라)
- 유효한 내부 링크
- 실질적인 고유 가치
- 광고/제휴 고지
- 허위 데이터 없음
- 승인 상태
- 이미지 권리 상태 검증
- 중복성 점검

# 14. 검색, 필터 및 탐색

정적 사이트 특성을 고려하여 검색 방식을 명확히 결정한다.

가능한 옵션:

1. 빌드 시 생성한 작은 검색 인덱스를 브라우저에서 검색
2. 규모가 커지면 외부 검색 서비스 사용(비용, 개인정보, 운영 복잡성 평가 후)
3. 지역/카테고리의 정적 목록과 필터를 활용한 탐색

첫 버전에서는 실제 데이터 규모에 맞는 가장 단순한 방법을 선택한다.

검색 기능 요구:

- 호텔명과 지역명 검색
- 지원되는 경우에만 검증된 태그/편의시설 필터
- 검색어가 없는 경우 기본 안내
- 검색 결과 없음 상태
- 잘못된 입력에 대한 안전한 처리
- 키보드 접근성
- 모바일에서 검색 결과의 가독성
- 필터 초기화
- 검색 결과의 정렬 기준 설명
- 지원하지 않는 필터는 노출하지 않음

정적 검색 인덱스에 비밀 데이터나 개인 데이터를 포함하지 않는다. 검색어를 서버로 전송하지 않는 구조라면 그 사실을 개인정보 설명에 정확하게 반영한다.

# 15. 성능, 접근성, 보안

## 15.1 성능

- 정적 HTML 우선
- 불필요한 클라이언트 JS 최소화
- 이미지 크기 지정
- 반응형 이미지 제공
- 아래쪽 이미지 lazy loading
- 필요한 경우에만 프리로드
- 폰트 파일 크기와 로딩 전략 검토
- 중복 라이브러리 제거
- 페이지별 번들/자산 크기 점검
- 주요 페이지의 Lighthouse 또는 동등한 검사 실행
- Core Web Vitals에 영향을 주는 요소 파악

성능 점수를 조작하거나 실제 측정하지 않은 점수를 보고하지 않는다.

## 15.2 접근성

WCAG 2.2 AA를 목표 기준으로 삼고 가능한 범위에서 검사한다.

- 시맨틱 HTML
- 키보드 탐색
- 가시적인 포커스
- 적절한 대비
- 이미지 대체 텍스트
- 폼 레이블 및 오류 메시지
- 링크 목적이 명확한 문구
- 제목 계층
- 메뉴 열림/닫힘 상태 전달
- `prefers-reduced-motion`
- 터치 대상 크기
- 스크린 리더에 불필요한 반복 정보 방지

자동 검사만으로 접근성이 완전히 보장된다고 주장하지 않는다. 핵심 흐름은 키보드와 화면 크기를 바꾸어 직접 확인한다.

## 15.3 보안

- 비밀값은 서버/빌드 환경의 비공개 변수로 보관한다.
- 공개 변수에 API 키를 넣지 않는다.
- 입력값을 검증하고 URL 프로토콜을 제한한다.
- 사용자 제공 문자열을 HTML로 무분별하게 삽입하지 않는다.
- 외부 API 오류와 응답 크기를 제한한다.
- 의존성을 최소화하고 취약점을 확인한다.
- 로그에 비밀값을 출력하지 않는다.
- 외부 링크와 새 탭 동작을 안전하게 처리한다.
- 정적 사이트에서 비밀값을 보호할 수 있다고 오해하지 않는다. 빌드 결과물에 포함된 값은 공개될 수 있다.
- 향후 관리 기능/로그인 기능을 추가할 경우 별도 위협 모델과 권한 검사를 설계한다.

# 16. 개인정보, 고지, 분석

사이트에서 실제로 사용하는 서비스에 맞추어 개인정보처리방침을 작성한다. 복사한 일반 템플릿을 실제 동작과 맞지 않게 게시하지 않는다.

검토할 항목:

- 서버/호스팅 로그
- 분석 도구
- AdSense
- 제휴 추적
- 쿠키 또는 유사 기술
- 외부 링크
- 문의 폼이 있는 경우 입력 정보
- 데이터 보유 기간
- 사용자 권리와 문의 방법
- 제3자 제공/처리 관련 사항

실제로 사용하지 않는 분석 도구나 쿠키를 사용하는 것처럼 작성하지 않는다. 반대로 실제로 데이터를 수집하면서 개인정보처리방침에서 누락하지 않는다.

운영자의 법적 의무는 서비스 대상 국가, 이용자, 실제 데이터 처리 방식에 따라 달라질 수 있으므로 게시 전 확인한다.

# 18. 배포 설계

## 18.1 기본 원칙

배포는 개발 작업과 분리한다. 프로덕션 도메인, Cloudflare Pages 프로젝트, DNS 설정은 사용자의 명시적 승인 없이는 변경하지 않는다.

정적 배포가 적합한 경우 Astro의 정적 출력 모드를 선택한다. API를 추가해야 한다면 정적 사이트와 서버 기능의 경계, 호스팅 지원 여부, 비밀값 관리 방식을 별도로 설계한다.

## 18.2 배포 환경

최소한 다음을 분리한다.

- 로컬 개발
- Preview/검토
- Production

환경별 설정을 분리하고 프로덕션 도메인, canonical, 제휴 설정, 광고 설정이 Preview에 잘못 적용되지 않도록 한다.

## 18.3 환경변수

필요한 경우 다음과 같은 변수 이름을 사용할 수 있다. 실제 아고다 API 문서와 계정 권한에 따라 조정한다.

```dotenv
# 예시 이름이며, 실제 API 권한/문서 확인 후 필요한 변수만 사용한다.
AGODA_API_KEY=
AGODA_API_BASE_URL=
AGODA_PARTNER_ID=
PUBLIC_SITE_URL=
PUBLIC_ADSENSE_CLIENT=
PUBLIC_ADSENSE_SLOT_HOME=
PUBLIC_ADSENSE_SLOT_CONTENT=
```

주의:

- 실제 API 키의 이름과 인증 방식은 공식 문서에 맞춘다.
- `AGODA_API_KEY` 같은 비밀값을 `PUBLIC_` 접두사 변수로 만들지 않는다.
- 비밀값은 빌드 결과나 클라이언트 JS에 포함되면 안 된다.
- 사이트 URL과 광고 ID는 공개 가능한 값일 수 있지만 환경별로 검증한다.
- 비밀값이 없는 환경에서는 관련 기능이 명확히 비활성화되고, 사이트의 기본 기능은 가능한 한 정상 작동해야 한다.

## 18.4 도메인과 기존 사이트 보호

- 기존 `cozytrip.kr` 사이트를 교체하지 않는다.
- 새 프로젝트가 별도의 출력 디렉터리를 사용하도록 한다.
- 도메인 이전/리디렉션은 사용자가 결정하기 전까지 하지 않는다.
- 새 프로젝트의 배포 설정이 기존 프로젝트와 혼동되지 않도록 문서화한다.
- 프로덕션 공개 전 sitemap, canonical, robots, 광고 ID, 제휴 링크를 확인한다.

# 20. 운영 및 유지보수

## 20.1 정기 점검

정기적으로 다음을 점검할 수 있는 도구 또는 체크리스트를 제공한다.

- 호텔 공식 정보 변경
- 호텔 운영/브랜드 변경
- 주소/교통 정보 변경
- 예약 링크 상태
- 제휴 프로그램 정책 변경
- 이미지 권리/사용 조건

- 깨진 내부/외부 링크
- 중복/얇은 콘텐츠
- SEO 메타데이터 누락
- AdSense 코드/정책 변화
- 개인정보 처리 방식 변화

## 20.2 정보 만료 정책

정보 종류별로 재검토 주기를 설정한다. 예를 들어 가격·재고·프로모션은 매우 빠르게 변할 수 있고, 호텔 주소나 공식 명칭은 상대적으로 덜 자주 바뀔 수 있다. 구체적인 주기는 출처와 실제 데이터 갱신 방식에 따라 정한다.

오래된 정보가 자동으로 최신 정보처럼 표시되지 않도록 한다. 재검토가 필요한 페이지는 상태와 날짜를 표시하고, 중요한 정보가 오래되면 예약 CTA 또는 공개 상태를 재검토한다.

## 20.3 콘텐츠 운영 보고서

운영자가 다음을 확인할 수 있도록 요약 보고서를 생성한다.

- 전체 호텔 레코드 수
- 승인된 콘텐츠 수
- 초안 수
- 출처 누락 항목
- 이미지 권리 미확인 항목
- 제휴 링크 미확인/실패 항목
- 재검토 기한이 지난 페이지
- 내부 링크 오류
- 제목/메타 설명 누락
- 중복 콘텐츠 경고
- 마지막 빌드/검증 결과

보고서는 실제 데이터에서 계산하고 숫자를 임의로 만들지 않는다.

| UI/반응형 검사   | 실행/미실행    | 실제 확인 범위   |
| 배포             | 실행/미실행    | 실제 상태        |

## 5. 사용자에게 필요한 설정

- 아고다 계정/API 권한
- 필요한 비밀 환경변수
- AdSense 클라이언트/슬롯 ID
- 운영자 검토가 필요한 콘텐츠
- 도메인/배포 관련 결정

## 6. 미완료/제한 사항

- 접근 권한 부족
- API 문서 미확인
- 이미지 권리 미확인
- 외부 계정 설정 필요
- 자동화하지 않은 항목
- 추가 검증이 필요한 부분

## 7. 기존 프로젝트 보호 확인

- 변경한 기존 파일이 있는지
- 새 프로젝트 외부의 설정을 수정했는지
- Git 상태와 diff 결과
- 프로덕션 배포/도메인 변경 여부

실제로 확인하지 않은 항목을 완료했다고 보고하지 않는다.

# 22. 반드시 피해야 할 구현

다음은 금지한다.

- 기존 프로젝트를 새 프로젝트로 덮어쓰기
- 기존 사이트의 파일이나 설정을 무단 삭제/수정
- 검증되지 않은 API 엔드포인트 또는 필드를 발명
- 호텔 가격/재고/평점/리뷰/거리/편의시설을 추측으로 채움
- 실제 투숙하지 않았는데 후기처럼 작성
- 타 사이트의 글을 문장만 바꾸어 복제
- 무단 이미지 수집 또는 재사용
- 권한 없는 스크래핑/API 호출
- 가짜 호텔/가짜 제휴 링크를 실제 데이터처럼 공개
- API 키를 브라우저에 노출
- 광고를 콘텐츠나 예약 버튼처럼 위장
- 광고 클릭을 유도
- 승인되지 않은 콘텐츠를 자동 공개
- 키워드만 다른 얇은 페이지를 대량 생성
- 실제로 실행하지 않은 테스트를 통과했다고 보고
- 승인 없이 프로덕션 배포
- 승인 없이 도메인/DNS 변경
- 확인되지 않은 수익·AdSense 승인·SEO 순위를 보장

# 23. 최종 실행 지시

이 문서의 요구사항을 바탕으로 실제 프로젝트를 구현한다.

1. 먼저 작업 공간과 Git 상태를 조사한다.
2. 기존 웹사이트 파일을 수정하지 않는 독립 디렉터리를 만든다.
3. 기술 스택과 구조를 확정하고 문서화한다.
4. 콘텐츠 모델과 검증을 먼저 구현한다.
5. 검증된 데이터만 사용하는 핵심 페이지와 모던 UI/UX를 구축한다.
6. 콘텐츠 자동화는 초안 생성과 품질 검사부터 구현하고, 승인되지 않은 콘텐츠의 자동 게시를 금지한다.
7. 아고다 통합은 실제 계정 권한과 공식 문서로 확인된 범위에서만 구현한다.
8. AdSense는 정책과 실제 설정을 확인한 뒤 준비하되, 승인 또는 수익을 보장하지 않는다.
9. 모든 주요 검사와 빌드를 실제 실행한다.
10. 변경 사항과 제한을 보고한다.
11. 배포·도메인 변경·기존 사이트 교체는 별도의 명시적 승인 없이는 실행하지 않는다.

**우선순위:** 데이터 신뢰성 및 권리 준수 → 기존 프로젝트 보호 → 콘텐츠의 실질적 가치 → 접근성/사용성 → SEO → 수익화 배치 → 시각적 완성도.

**완료 정의:** 단순히 보기 좋은 페이지를 만드는 것이 아니라, 근거 있는 일본 호텔 콘텐츠를 검토 가능한 초안으로 자동화하고, 사용자가 승인한 콘텐츠만 안전하게 게시할 수 있으며, 아고다 제휴와 AdSense를 정책에 맞게 연결할 수 있도록 설계·구현·검증·문서화된 독립 웹사이트 프로젝트를 완성하는 것이다.
