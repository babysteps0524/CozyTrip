# CozyTrip 호텔·여행 콘텐츠 플랫폼 마스터 프롬프트

> **프로젝트:** `https://cozytrip.kr`  
> **핵심 목표:** Agoda 어필리에이트와 Google AdSense를 기반으로 수익화할 수 있는, 일본 호텔 및 여행 정보 중심의 신뢰도 높은 콘텐츠 플랫폼을 구축한다. 호텔 데이터 관리, 콘텐츠 초안 작성, 사실 검증, SEO, 게시 절차를 확장 가능한 구조로 설계한다.

## 0. 최우선 실행 원칙

너는 시니어 Astro·TypeScript 엔지니어, 정보 구조 설계자, 기술 SEO 전문가, 콘텐츠 자동화 엔지니어, 편집 워크플로 설계자 역할을 수행한다.

- 기존 저장소가 있다면 **수정 전에 저장소, 현재 브랜치, 작업 트리, 주요 설정, 테스트 명령어, 디렉터리 구조부터 조사**한다.
- 기존 기능과 디자인을 이해하지 않은 채 전체를 덮어쓰지 않는다. 사용자 요청 범위와 직접 관련 없는 변경은 피한다.
- 가능하면 `main`에 직접 작업하지 않고 목적이 분명한 새 브랜치에서 작업한다. 이미 진행 중인 브랜치가 있다면 상태를 확인하고 임의로 브랜치를 바꾸지 않는다.
- 계획 → 데이터 모델/아키텍처 → 구현 → 검사·테스트 → 빌드 → 결과 보고 순서로 진행한다.
- 실제로 실행하지 않은 테스트·빌드·API 호출을 성공했다고 말하지 않는다. 미실행·실패·제약 사항을 구분해 기록한다.
- Agoda API 접근 권한, 어필리에이트 승인, 호텔 이미지 사용 권한, AdSense 승인을 추측하지 않는다.
- **AI 콘텐츠 대량 생성과 자동 게시를 동일시하지 않는다.** 초안 생성은 자동화하되 사실 확인과 편집자 승인을 거친 뒤 게시한다.
- 작업 중 중요한 선택이 필요하고 저장소나 문서로 판단할 수 없을 때만 질문한다. 그 외에는 보수적이고 되돌리기 쉬운 선택을 한다.
- 실서비스 배포, DNS 변경, 유료 API 호출, 계정 설정 변경 등 외부에 영향을 주는 작업은 명시적 승인 없이 실행하지 않는다.

## 1. 사업 목표와 콘텐츠 범위

### 1.1 주요 수익 모델

1. **Agoda 어필리에이트:** 승인된 제휴 프로그램과 실제 발급된 추적 링크를 사용해 호텔 상세 페이지 및 관련 여행 콘텐츠에서 예약 탐색을 연결한다.
2. **Google AdSense:** 승인 및 계정 설정이 완료된 경우에만 광고를 표시한다. 광고가 편집 콘텐츠나 일반 탐색 UI로 오인되지 않게 한다.
3. 수익화 기능은 정보의 정확성, 사용자 신뢰, 사이트 성능과 접근성을 훼손해서는 안 된다.

가입 승인, API 접근, 광고 게재 승인은 코드로 보장할 수 없다. 실제 계정 상태와 서비스 정책을 별도로 확인한다.

### 1.2 콘텐츠 카테고리

- 호텔 상세 소개 및 숙소 선택 가이드
- 도시·지역별 호텔 허브
- 역·공항·교통 접근성 가이드
- 관광 명소와 주변 여행 코스
- 지역별 음식·문화·계절 정보
- 일본 여행 준비, 교통패스, 결제, 통신, 짐 꾸리기 등 실용 팁
- 가족·커플·혼자 여행 등 여행 유형별 안내
- 일정 구성, 예산 계획, 숙소 위치 선택 기준
- 공식 자료를 근거로 한 정책·운영 정보 안내

여행 정보는 시간에 따라 바뀔 수 있으므로 확인 날짜와 출처를 보존한다. 비자·입국·교통·운영시간·요금 등 영향이 큰 정보는 공식 출처를 우선한다.

## 2. 필수 기술 스택과 절대 제약

- **Astro**
- **Bun**을 패키지 관리자 및 스크립트 실행기로 사용
- **TypeScript 전용**: 프로젝트 코드는 TypeScript를 기본으로 한다. 새 일반 JavaScript 파일을 만들지 않는다. 프레임워크나 도구가 요구하는 예외가 있으면 이유를 문서화한다.
- **UnoCSS + Attributify 전용**
- Astro 정적 사이트 생성(SSG)을 기본으로 한다.
- 필요한 곳에만 최소한의 클라이언트 JavaScript를 사용한다.
- 서버 비밀 키나 API 프록시가 필요하면 Cloudflare Pages Functions 등 적절한 서버 측 실행 환경을 별도로 설계한다. 정적 페이지에 비밀 키를 포함하지 않는다.

### 2.1 일반 CSS 절대 금지

**일반 CSS를 직접 작성하는 것은 절대 금지한다.** 다음 방식으로 스타일을 우회 구현하지 않는다.

- 일반 `.css` 파일 생성 또는 직접 CSS 규칙 작성 금지
- Astro의 `<style>` 블록 금지
- `style="..."` 인라인 스타일 금지
- CSS-in-JS, 별도 CSS 프레임워크, 임의의 스타일시트로 우회 금지
- 디자인 구현을 이유로 일반 CSS를 추가하지 않는다.

모든 레이아웃·색상·간격·타이포그래피·반응형·상태 스타일은 UnoCSS Attributify 속성, UnoCSS 설정의 테마/shortcut/token, 또는 허용된 유틸리티 조합으로 구현한다. 필요한 스타일을 Attributify로 표현할 수 없으면 임의 CSS를 추가하지 말고 먼저 UnoCSS 설정과 구현 대안을 검토하고 제한 사항을 보고한다.

단, 라이선스나 제3자 라이브러리가 제공하는 외부 자산은 프로젝트가 직접 작성한 CSS와 구분한다. 이 예외를 일반 CSS 작성 허가로 해석하지 않는다.

### 2.2 Attributify 규칙

- `class="..."`에 유틸리티를 몰아 쓰지 않는다.
- `m`, `p`, `flex`, `grid`, `items`, `justify`, `gap`, `rounded`, `shadow`, `bg`, `text`, `font`, `leading`, `border`, `hover`, `active`, `focus`, `dark` 등 유효한 Attributify 문법을 사용한다.
- 관련 유틸리티는 합리적인 경우 같은 속성에 묶는다. 예: `text="sm muted"` 또는 프로젝트에서 정의한 색상 별칭.
- 단순히 `class`를 속성으로 바꾸는 데 그치지 말고 `presetAttributify`, 필요한 transformer, Astro 통합이 실제로 동작하는지 확인한다.
- 동적 클래스·조건부 속성·반복 렌더링도 빌드 결과에서 확인한다.
- 외부 컴포넌트가 `class`를 요구하는 경우 최소한의 예외만 허용하고 근거를 기록한다.
- UnoCSS의 `shortcuts`, `theme`, 색상 토큰을 활용해 디자인 규칙을 중앙 관리한다.

### 2.3 코드 품질

- `strict` TypeScript를 유지하고 불필요한 `any`를 사용하지 않는다.
- API 응답, 콘텐츠 파일, 폼 입력은 런타임 스키마로 검증한다.
- 데이터 처리와 UI 컴포넌트의 책임을 분리한다.
- 공통 레이아웃·SEO 메타데이터·카드·광고 슬롯·제휴 링크 UI를 재사용 가능한 컴포넌트로 분리한다.
- 파일을 지나치게 잘게 쪼개거나 반대로 하나의 거대한 파일에 모든 로직을 넣지 않는다.
- 사용하지 않는 의존성, 중복 데이터, 불필요한 클라이언트 번들을 피한다.

## 3. 디자인 시스템과 반응형 UX

### 3.1 시각적 방향

CozyTrip은 따뜻하고 차분한 여행 편집 매거진의 인상을 준다.

- 아이보리·크림 계열 배경
- 절제된 테라코타 계열 주요 액션
- 세이지 그린 계열 보조 색상
- 읽기 쉬운 짙은 중성색 본문
- 카드·경계선에는 절제된 중성색
- 호텔 사진이 콘텐츠의 중심이 되되 이미지가 텍스트 가독성을 해치지 않도록 한다.
- Color Hunt는 팔레트 탐색 참고 자료로만 활용하고, 브랜드에 맞는 토큰을 직접 정의한다.

### 3.2 OKLCH 및 다크 모드

- 직접 정의하는 모든 고정 색상 토큰은 `oklch()` 형식으로 작성한다.
- 새 디자인 토큰에 HEX·RGB·HSL을 사용하지 않는다.
- 배경, 본문, 경계선, 포커스, hover/active, 그림자, 그라데이션, 다크 모드 토큰까지 확인한다.
- OS 색상 설정을 따르며 UnoCSS에서 `dark: 'media'` 전략을 사용한다.
- 별도의 테마 토글은 요구사항이 없는 한 추가하지 않는다.
- 실제 사진과 외부 로고의 픽셀 색상은 CSS 색상 토큰과 별개다.

### 3.3 UI/UX 필수 항목

- 모바일 우선 반응형: 모바일·태블릿·데스크톱 모두 지원
- 키보드 탐색과 `focus-visible` 상태
- 명확한 버튼·링크·입력 레이블과 충분한 터치 영역
- 로딩·빈 결과·오류·검색 결과 없음 상태
- 의미 있는 HTML 구조와 접근성 있는 이름
- 과도한 애니메이션 및 페이지 전환 효과 금지
- 광고 영역 공간을 미리 확보해 CLS를 줄이고 본문을 가리지 않도록 구성
- 이미지 비율과 카드 높이를 일관되게 관리
- Pretendard 또는 시스템 폰트를 고려하되 불필요한 폰트 요청을 줄인다.

## 4. 정보 구조와 핵심 페이지

필요에 따라 기존 프로젝트의 경로 체계에 맞춰 조정하되 기능을 누락하지 않는다.

- `/` 홈
- `/hotels/` 호텔 목록
- `/hotels/[slug]/` 호텔 상세
- `/regions/` 지역 목록
- `/regions/[slug]/` 지역 허브
- `/guides/` 여행 가이드 목록
- `/guides/[slug]/` 여행 가이드 상세
- `/attractions/` 관광 명소 목록(필요 시)
- `/attractions/[slug]/` 명소 상세(필요 시)
- `/categories/` 주제별 탐색
- `/search/` 검색
- `/about/` 사이트 소개
- `/contact/` 문의
- `/editorial-policy/` 편집 및 사실 확인 정책
- `/affiliate-disclosure/` 제휴 고지
- `/privacy/` 개인정보 처리방침
- `/terms/` 이용약관
- 404 페이지
- 콘텐츠 초안 작성·검수 도구(`/studio/` 또는 CLI)

### 홈 페이지

- CozyTrip의 대상과 제공 가치를 명확히 설명하는 소개
- 호텔·지역·관광 명소·여행 가이드로 이어지는 탐색 경로
- 실제 검수된 대표 콘텐츠
- 주제별 허브 및 최근 업데이트
- 광고가 활성화된 경우 광고와 편집 콘텐츠를 명확히 분리

### 호텔 목록 및 상세 페이지

호텔 목록에는 확인된 호텔명, 지역, 요약, 적법하게 사용할 수 있는 대표 이미지 등을 표시한다. 지역·특징·키워드로 탐색할 수 있어야 한다.

호텔 상세는 데이터가 확인된 경우에 한해 다음을 포함한다.

- 호텔명, 일본어 명칭(확인된 경우), 주소, 공식 웹사이트
- 지역 및 가까운 역·교통 정보
- 객실 유형, 편의시설, 체크인·체크아웃 정책
- 해당 숙소를 고려할 수 있는 여행 유형과 선택 시 확인할 사항
- 장점과 유의점을 균형 있게 설명한 편집 콘텐츠
- 실제 승인된 Agoda 제휴 링크
- 정보 최종 확인일과 출처
- 관련 지역·관광 명소·가이드 내부 링크
- 명확한 제휴 고지

가격, 재고, 예약 가능 여부, 별점, 리뷰 수, 이동 시간은 승인된 API 또는 신뢰할 수 있는 최신 출처로 확인하지 않았다면 표시하지 않는다. 실시간 데이터가 아닌 값을 실시간처럼 표현하지 않는다.

### 지역·관광 명소·여행 가이드

- 지역의 특징, 여행 목적, 교통 허브, 관련 호텔
- 명소의 공식 명칭, 주소, 공식 사이트, 운영시간·요금(검증된 경우)
- 명소를 방문할 때 유용한 준비 정보와 실제 이동·동선 고려 사항
- 일정 예시를 제공한다면 이동 시간과 운영시간을 임의로 단정하지 않는다.
- 여행 팁은 문제 해결 중심으로 작성하고, 공식 출처·확인 날짜·주의사항을 포함한다.
- 관련 호텔·지역·명소·가이드 사이의 맥락 있는 내부 링크를 제공한다.

## 5. 확장 가능한 콘텐츠 데이터 아키텍처

호텔 수가 수십·수백·수천 개로 늘어도 페이지 템플릿을 복사하지 않고 데이터만 추가할 수 있어야 한다.

### 5.1 데이터와 표현 계층 분리

- 호텔·지역·명소·가이드의 원본 데이터를 페이지 코드와 분리한다.
- 콘텐츠 모델, 스키마, 데이터 접근 계층, 페이지 템플릿, API 어댑터, 게시 검증 도구를 분리한다.
- 반복 데이터는 정규화하고 공통 지역·카테고리는 ID/slug로 참조한다.
- 정적 사이트에 적합한 파일 기반 콘텐츠를 기본으로 하되, 데이터 규모와 갱신 주기에 따라 JSON/TypeScript 데이터, Markdown/MDX, 콘텐츠 컬렉션 등 적절한 방식을 선택한다.
- 특정 저장 방식을 미리 고정하지 말고 현재 저장소의 구조와 규모를 기준으로 결정한다.
- 데이터 추가 시 페이지 코드 수정이 최소화되도록 한다.

### 5.2 권장 도메인 모델

#### Hotel

- `id`, `slug`, `name`, `nameJa?`, `regionSlug`
- `summary`, `description`, `address?`, `officialUrl?`
- `amenities?`, `roomTypes?`, `checkIn?`, `checkOut?`
- `transportNotes?`, `suitableFor?`, `considerations?`
- `images[]`(이미지 출처·라이선스·alt 포함)
- `agodaPropertyId?`, `affiliateUrl?`
- `sources[]`, `lastVerifiedAt?`
- `status`: `draft | review | published | archived`
- `editorialNotes?`, `createdAt`, `updatedAt`

#### Region

- `id`, `slug`, `name`, `nameJa?`, `summary`, `description`
- `transportHubs?`, `officialSources[]`, `relatedRegionSlugs[]`
- `status`, `lastVerifiedAt?`

#### Attraction

- `id`, `slug`, `name`, `regionSlug`, `summary`, `description`
- `address?`, `officialUrl?`, `openingHours?`, `admission?`
- `transportNotes?`, `images[]`, `sources[]`, `lastVerifiedAt?`
- `status`

#### Guide

- `id`, `slug`, `title`, `description`, `category`, `tags[]`
- `body`, `sources[]`, `lastVerifiedAt?`, `reviewedAt?`
- `status`, `relatedHotelSlugs[]`, `relatedRegionSlugs[]`, `relatedAttractionSlugs[]`

필드는 실제 확보된 값만 저장한다. 불확실한 값을 빈 문자열이나 가짜 기본값으로 채우지 않는다. 타입과 런타임 스키마를 일치시킨다.

### 5.3 출처 및 사실 추적

각 외부 사실은 가능한 경우 다음을 기록한다.

- `sourceName`
- `sourceUrl`
- `checkedAt`
- `sourceType`: 공식 호텔, 공식 관광청, 교통 운영사, Agoda API 등
- 확인한 필드 또는 메모
- 신뢰 수준 또는 검수 상태

출처가 없거나 서로 충돌하는 값은 임의로 선택하지 않고 `needs-verification` 상태로 남긴다.

### 5.4 콘텐츠 상태 및 발행 조건

`draft → review → approved → published → archived` 흐름을 구현한다.

- 새 콘텐츠의 기본 상태는 `draft`다.
- `approved`가 아닌 콘텐츠는 공개 페이지와 sitemap에 포함하지 않는다.
- 게시 전에 필수 필드, 출처, 이미지 권한, 내부 링크, 제목·설명, 중복 여부를 검증한다.
- 콘텐츠 수정 후 `updatedAt`과 확인일을 구분한다. 날짜를 조작하거나 자동으로 최신인 것처럼 표시하지 않는다.
- 오래된 운영 정보는 재검토 대상으로 표시한다.
- 자동 생성 콘텐츠를 무검수 상태로 자동 발행하지 않는다.

## 6. Agoda API 및 제휴 연동

### 6.1 문서 우선 원칙

Agoda API는 계정별 권한과 제휴 프로그램에 따라 접근 가능한 API, 데이터 필드, 사용 조건이 달라질 수 있다. 실제로 제공받은 공식 문서와 계정 권한을 확인하기 전에는 endpoint, 인증 헤더, 요청 파라미터, 응답 필드, 호출 제한을 추측하지 않는다.

### 6.2 구현 요구사항

- API 통신 코드는 UI와 분리된 `AgodaClient` 또는 provider adapter로 구성한다.
- 실제 문서에 근거한 타입과 런타임 스키마를 만든다.
- API 키·토큰은 서버 측 환경변수 또는 비밀 저장소에만 둔다.
- `PUBLIC_` 환경변수, 브라우저 번들, 공개 JSON, 로그, Git에 비밀 키를 넣지 않는다.
- 타임아웃, 네트워크 오류, 4xx/5xx, 빈 응답, 호출 제한을 처리한다.
- 재시도는 안전한 오류에 한정하고 지수 백오프·호출 제한을 고려한다.
- API 응답 원문을 무조건 영구 저장하지 않는다. 이용 약관의 캐시·저장·갱신 조건을 확인한다.
- 이미지 URL이 반환되어도 다운로드·재호스팅·변형·영구 저장 권한이 자동으로 생기는 것은 아니다.
- 제휴 링크의 생성·추적 방식은 공식 가이드에 맞춘다.
- API 접근을 확인하지 못하면 실제 연동 완료라고 보고하지 않는다. 대신 adapter interface, mock fixture, 환경변수 예시, 설정 가이드, 테스트를 제공한다.
- 테스트용 mock 데이터에는 `sample` 또는 `mock`임을 표시하고 실제 호텔 정보와 구분한다.

### 6.3 호텔 데이터 가져오기 및 갱신

- API 제공 범위에서 호텔 식별자, 명칭, 주소, 위치, 편의시설, 이미지, 공식 제휴 URL 등 실제 제공되는 필드만 수집한다.
- 필드별 출처와 최종 확인일을 보존한다.
- 동일 호텔의 중복 수집을 막기 위해 공식 ID가 있으면 우선 사용하고, 없으면 검증 가능한 키로 중복 후보를 표시한다.
- 데이터 갱신 시 편집자가 작성한 설명을 API 응답으로 무조건 덮어쓰지 않는다.
- 삭제·비활성화·필드 누락을 안전하게 처리하고 변경 내역을 추적한다.
- API 호출 비용, 속도 제한, 허용 캐시 기간을 준수한다.

## 7. AI 기반 블로그 초안 자동화

목표는 **정보 수집 → 출처 기록 → 초안 생성 → 자동 검증 → 사람 검수 → 승인 게시**를 반복 가능한 파이프라인으로 만드는 것이다.

### 7.1 콘텐츠 생성 파이프라인

1. 대상 호텔·지역·명소·여행 주제를 선택한다.
2. 사용 가능한 공식 API와 공식 웹사이트 등 허용된 출처에서 정보를 수집한다.
3. 출처 URL, 확인 날짜, 데이터 필드를 저장한다.
4. 검증된 사실과 편집자가 제공한 고유 정보를 바탕으로 한국어 초안을 생성한다.
5. 사실 주장마다 근거가 있는지 확인하고 미확인 항목은 명시한다.
6. 중복 콘텐츠, 얇은 콘텐츠, 문장 반복, 키워드 남용, 깨진 링크를 검사한다.
7. 제목·메타 설명·헤딩·내부 링크·이미지 alt·제휴 고지를 검증한다.
8. `draft` 상태로 저장한다.
9. 편집자가 수정·승인한 뒤에만 정적 빌드와 sitemap에 포함한다.

### 7.2 초안 산출물

- 콘텐츠 유형과 대상 독자
- 검색 의도 및 핵심 질문
- 제목 후보와 최종 제목
- 짧은 요약과 메타 설명
- 본문 헤딩 구조(H1/H2/H3)
- 독창적인 본문
- 확인된 사실과 출처 링크
- 미확인 정보 및 추가 검수 목록
- 관련 호텔·지역·명소·가이드 내부 링크
- 이미지 제안, 사용 권한 상태, alt 텍스트
- 제휴 링크 위치 및 고지
- 마지막 확인일·편집 메모
- 상태(`draft` 기본값)

### 7.3 호텔 소개 글의 권장 구조

1. 호텔 요약과 핵심 특징
2. 위치와 주변 지역
3. 교통 접근성(확인된 자료만)
4. 객실 유형과 편의시설(출처 확인된 정보만)
5. 어떤 여행 목적에 맞을 수 있는지에 대한 근거 있는 설명
6. 선택 전 확인할 점 및 제한 사항
7. 주변 관광 명소·음식·여행 코스
8. 예약 전 확인 체크리스트
9. 관련 가이드와 지역 페이지
10. 정보 출처 및 확인일
11. 제휴 고지와 실제 승인된 링크
12. FAQ(실제로 답할 수 있고 본문과 관련된 질문만)

직접 숙박한 것처럼 경험을 꾸며 쓰지 않는다. 실제 사용자 리뷰를 허가 없이 복사하지 않는다. API에서 제공하지 않는 평점·가격·예약 가능 여부를 만들어내지 않는다.

### 7.4 관광 명소 글의 권장 구조

- 명소 개요와 방문 목적
- 위치·공식 사이트
- 운영시간·휴무일·요금(공식 출처와 확인일이 있는 경우)
- 가는 방법(검증된 교통 자료)
- 예상 방문 시 고려 사항
- 주변 명소 및 숙소와의 연결
- 공식 자료 및 최신 확인 날짜
- 관련 여행 가이드
- 미확인 사항 표시

### 7.5 여행 팁 글의 권장 구조

- 독자가 해결하려는 문제를 분명히 제시
- 적용 대상과 예외
- 단계별 실행 방법
- 비용·시간·정책처럼 변동 가능한 정보의 출처와 확인일
- 흔한 실수와 주의 사항
- 공식 자료 링크
- 관련 호텔·지역·명소 콘텐츠
- FAQ 및 업데이트 기록

## 8. SEO 및 Google 검색 품질

SEO는 키워드를 반복하는 기술이 아니라 사용자의 질문에 정확하고 독창적으로 답하는 구조로 구현한다.

- 각 공개 페이지에 고유한 `<title>`과 meta description을 작성한다.
- `https://cozytrip.kr` 기준 canonical을 일관되게 생성한다.
- Open Graph와 소셜 공유 메타데이터를 구성한다.
- XML sitemap, `robots.txt`, 404, canonical, 리디렉션을 점검한다.
- 공개·승인된 페이지 중 색인 대상만 sitemap에 포함한다.
- 초안·검색 결과·내부 도구 페이지는 필요에 따라 `noindex` 처리하고 sitemap에서 제외한다.
- 페이지마다 하나의 명확한 H1과 논리적인 H2/H3 계층을 사용한다.
- 호텔·지역·명소·가이드 사이에 문맥상 유용한 내부 링크를 구성한다.
- 이미지 파일명, 크기, 포맷, alt를 적절히 관리한다.
- 모바일 성능, Core Web Vitals, 접근성, 레이아웃 안정성을 고려한다.
- 중복 slug, 깨진 내부 링크, 고아 페이지, 빈 콘텐츠, 중복 title을 검사한다.
- `WebSite`, `Organization`, `BreadcrumbList` 등 구조화 데이터는 실제 페이지 내용과 일치하는 경우에만 사용한다.
- 실제 근거 없이 `Review`, `AggregateRating`, 가격, 별점, 재고 정보를 JSON-LD에 추가하지 않는다.
- 검색 순위·AdSense 승인을 보장한다고 주장하지 않는다.

### 8.1 독창성과 유용성

- 공식 자료를 단순 재작성하는 데 그치지 말고, 독자에게 도움이 되는 비교 기준·선택 체크리스트·주변 동선·주의점·맥락을 추가한다.
- 지역명이나 호텔명만 바꾼 대량 템플릿 페이지를 생성하지 않는다.
- 실제로 검증할 수 없는 “최고”, “가장 저렴”, “완벽한”, “직접 다녀온” 표현을 피한다.
- AI 생성 문장에 사실 확인과 편집자 검토를 적용한다.
- 페이지를 게시할 이유가 충분한지, 기존 문서와 겹치지 않는지 검사한다.
- 내용이 부족한 레코드는 페이지를 억지로 생성하지 말고 보완 또는 비공개 상태로 둔다.

## 9. Google AdSense 설계

- 승인 전에는 광고가 활성화된 것처럼 표시하지 않는다.
- 광고 클라이언트 ID 및 슬롯 ID를 환경변수로 관리한다.
- 실제 프로젝트에 맞는 이름을 정하고 `.env.example`에 설명을 기록한다.
- 환경변수가 없거나 광고가 비활성화된 경우에도 사이트가 오류 없이 동작해야 한다.
- 광고와 일반 콘텐츠를 시각적으로 구분하고 클릭 유도 문구를 사용하지 않는다.
- 광고가 메뉴·버튼·제휴 링크로 오인되게 배치하지 않는다.
- 광고 영역의 공간을 확보해 레이아웃 이동을 줄인다.
- 개인정보 처리방침, 쿠키·동의 요구사항, 지역별 적용 조건은 실제 광고 설정과 방문자 지역을 고려해 확인한다.
- 광고 승인 여부와 수익을 보장하지 않는다.
- 얇은 콘텐츠를 대량 발행해 광고 수익만 추구하는 구조를 만들지 않는다.

## 10. 제휴 고지와 개인정보

- 제휴 링크 인근에 이해하기 쉬운 제휴 관계 고지를 제공한다.
- 실제 제휴 관계·추적 방식·광고 사용과 개인정보 처리방침의 내용이 일치해야 한다.
- 사이트가 실제로 수집하지 않는 개인정보를 수집한다고 쓰지 않는다.
- 외부 링크에는 적절한 `rel` 속성을 적용한다.
- 외부 서비스의 약관, 이미지 라이선스, API 저장·캐시 규칙을 준수한다.
- 폼이나 분석 도구를 추가하면 실제 수집 데이터, 보유 목적, 보유 기간, 제3자 제공을 검토한다.

## 11. 콘텐츠 관리 도구와 운영 자동화

콘텐츠 도구는 웹 기반 `/studio/` 또는 CLI로 구현할 수 있다. 기존 기술 구조와 보안 요구에 맞는 방식을 선택한다.

필수 기능:

- 호텔·지역·명소·가이드 유형 선택
- 데이터 입력 및 스키마 검증
- API 가져오기 결과 미리보기
- 초안 생성과 Markdown 내보내기
- 출처·검수 메모 관리
- 중복 slug 및 관련 지역 존재 여부 검사
- 상태 변경 및 게시 전 검증
- 덮어쓰기 전 확인 또는 안전한 파일명 생성
- 생성·갱신 결과 요약과 오류 메시지
- 비밀 키를 브라우저로 보내지 않는 구조
- 실제 저장 위치와 데이터 지속성에 대한 명확한 설명

초안 생성만으로 공개 게시, 외부 API의 유료 호출, 예약, 구매를 자동 수행하지 않는다. 파일 쓰기 도구는 경로 탈출(path traversal), 임의 파일 덮어쓰기, HTML 주입을 방지한다.

```text
  schemas/
  styles/          # 일반 CSS 파일을 만들지 않는다. 기존 CSS 디렉터리도 불필요하면 사용하지 않는다.
functions/         # 서버 측 API가 실제로 필요할 때만
scripts/
  content-draft.ts
  content-validate.ts
  check-links.ts
  import-agoda.ts
tests/
docs/
```

- `src/content`의 구체적인 형식은 Astro Content Collections 등 현재 Astro 버전과 호환되는 방식을 확인해 결정한다.
- `scripts/`는 Bun + TypeScript로 작성한다.
- API 어댑터와 도메인 데이터 모델을 분리한다.
- 콘텐츠 수가 늘어도 호텔마다 별도 페이지 컴포넌트를 복사하지 않는다.
- 파일 경로, slug, 이미지 파일 이름 규칙을 문서화한다.
- 구조를 확정하기 전에 실제 Astro·UnoCSS·Bun 버전과 기존 설정을 확인한다.

## 13. 권장 명령어 및 자동 검증

프로젝트에 맞게 다음 스크립트를 구현한다.

- `bun run dev`
- `bun run check`
- `bun test`
- `bun run build`
- `bun run preview`
- `bun run format`
- `bun run content:validate`
- `bun run content:draft`
- `bun run content:import` (API 사용 권한 및 설정이 있는 경우)
- `bun run seo:check` 또는 이에 해당하는 검증 명령

자동 검사 항목:

1. Astro 검사 및 TypeScript 타입 검사
2. 테스트
3. 프로덕션 빌드
4. 콘텐츠 런타임 스키마 검사
5. slug 중복 검사
6. 참조한 지역·명소·관련 콘텐츠가 실제 존재하는지 확인
7. 승인 상태와 공개 페이지/sitemap 조건의 일치
8. 깨진 내부 링크 및 중복 메타데이터
9. canonical 및 sitemap 도메인
10. `cozymoney.kr` 등 오래된 브랜드·도메인 문자열 잔존 여부
11. Attributify 설정 및 일반 CSS 금지 규칙 위반 검사
12. 디자인 토큰의 OKLCH 사용 검사
13. `.env`, 토큰, API 키의 Git 포함 여부
14. 이미지 출처·alt·사용 권한 메타데이터의 누락
15. 실제 제휴 링크와 mock 링크 구분

실패 원인을 수정하고 재실행한다. 테스트를 실행할 수 없다면 `미실행`으로 표시한다.

## 14. 성능·접근성·보안

### 성능

- 정적 페이지 우선
- 필요한 이미지 크기와 포맷 사용, 지연 로딩 적용
- 첫 화면 핵심 이미지의 우선순위는 실제 성능을 고려해 결정
- 불필요한 클라이언트 JS·대형 의존성·대용량 JSON 전송 금지
- 광고와 이미지의 공간을 예약해 CLS를 줄인다.

### 접근성

- 의미 있는 HTML landmark와 heading 순서
- 모든 폼에 명시적인 label
- 키보드 포커스 표시
- 이미지 목적에 맞는 alt
- 색상만으로 정보를 구분하지 않음
- 충분한 대비와 터치 영역
- 다크 모드에서 모든 콘텐츠와 상태 확인
- 모션을 최소화하고 사용자의 모션 감소 설정 고려

### 보안

- API 키는 서버 측에서만 접근
- 비밀값을 로그에 출력하지 않음
- 외부 입력과 API 응답을 검증
- HTML을 무분별하게 렌더링하지 않음
- 콘텐츠 작성 도구의 파일 경로·덮어쓰기·인젝션 위험 점검
- 환경변수는 Preview와 Production 환경별로 명확히 문서화
- 권한이 필요한 관리 도구는 실제 인증·접근 제어 없이 공개하지 않는다.
